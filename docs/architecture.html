Tamis Architecture

How the app is put together: the layers and the rules that keep them apart, the threading model, and the persistence formats — plus why the non-obvious parts are the way they are.

Tamis is a single-window PySide6 desktop app for culling and lightly editing one folder of photos at a time — about 5,800 lines across roughly 30 modules. This document covers the software structure. For how the face-recognition algorithm works (detection, embedding, identity matching), see Face Detection & Recognition instead.

1. Layers and dependency rules

Dependencies point downward only. Nothing in a lower layer imports from a higher one.

                   main.py  →  tamis.app          process entry, logging, excepthook
                                    │
                               MainWindow          window, menus, shortcuts, navigation
                                /        \
                 EditController          FaceRecognitionController
                     │                       │
 ┌───────────────────┴───────────┬───────────┴──────────────────────┐
 │                               │                                  │
views/                       editing/                        recognition/
(Qt widgets,                 (Pillow ops,                     (models, matching,
 presentational)              undo/redo)                       per-folder cache)
 │                               │                                  │
 └───────────────┬───────────────┴──────────────────────────────────┘
                 │
        models/   io_ops/   thumbnails.py   metadata.py   persistence.py

The boundaries are enforced by discipline rather than tooling, so the rules are worth stating explicitly:

RuleWhy
recognition/ imports no Qt, except worker.py Keeps detection and matching testable without a QApplication, and makes the Qt seam a single, obvious file.
views/ are presentational: they emit signals describing an intent, and never mutate app state A panel can be exercised in a test by connecting to its signals, and the decision about what an intent means lives in one place.
persistence.py imports nothing from the rest of the app Every layer that writes a sidecar needs it, so any dependency would create a cycle.
Controllers own mutable state; MainWindow owns only cross-feature glue See §3.
models/ and io_ops/ know nothing about Qt Pure data and file operations, directly unit-testable.

Only two modules import torch: recognition/detector.py and recognition/embedder.py. Everything else in recognition/ is plain numpy.

The optional-dependency boundary

Face recognition depends on torch/torchvision/facenet-pytorch, an optional extra (requirements-recognition.txt). The whole feature degrades to “not available” rather than breaking the app, via a single guarded import in main_window.py: 

try:
    from tamis.controllers.face_recognition_controller import FaceRecognitionController
    from tamis.views.face_panel import FacePanel
    from tamis.views.search_panel import SearchPanel
    RECOGNITION_AVAILABLE = True
except ImportError:
    RECOGNITION_AVAILABLE = False

Every use of the feature is then guarded by RECOGNITION_AVAILABLE, and the Face Recognition / Search by Name tabs are simply never added.

Known inaccuracy

views/face_panel.py states in its docstring that it has no dependency on tamis.recognition and so stays importable without the optional deps. That is no longer true — it imports DEFAULT_MIN_CONFIDENCE from recognition.detector, which imports torch at module level. The guarded import above covers it, so nothing breaks, but the docstring overstates the isolation.

3. Controllers, and what MainWindow keeps

EditController and FaceRecognitionController each own one feature's mutable state and wire their panel's signals to it. Neither knows the other exists.

MainWindow keeps only what genuinely spans both:

  • Mode exclusivity. Crop mode and Edit Faces mode both interpret mouse drags on the same ImageViewer, so they cannot both be active. EditPanel.crop_mode_toggled and FacePanel.edit_mode_toggled are connected to small MainWindow wrappers that turn the other mode off before delegating.
  • Overwrite invalidation. Saving over a photo makes its cached face boxes wrong — they were computed against the pre-edit geometry — so all three save signals route through MainWindow._save_edit, which handles that side effect.
  • Search cancellation. A merge or forget in Manage People can remove a Person that a running SearchPanel scan holds a reference to. MainWindow is the only object that knows about both.

Everything else is connected directly from panel to controller. The pattern is deliberate: where a signal is not connected in the obvious place, the controller carries a comment explaining which cross-feature concern moved it up.

4. Threading

This is the subtlest part of the app and the source of most of its historical bugs. Three pools, with different rules.

4.1 The shared pool — QThreadPool.globalInstance()

Runs thumbnail decoding, full-image decoding and metadata reading, prioritised so the photo on screen is not stuck behind background work:

WorkPriority
Full image for the current photo10
Metadata for the current photo0
Filmstrip thumbnails0

Priority orders the queue; it cannot preempt a running task

Face detection used to run here at priority 10. Because each detection worker held a thread while blocked on the model lock, enough of them occupied every thread in the pool and left nothing to decode the visible photo — measured at 152 ms → 2103 ms for the displayed image after browsing past 24 photos. Priority did not help, because the threads were already busy. Hence §4.2.

4.2 The detection pool — maxThreadCount=1

Owned by FaceRecognitionController. Detection is single-threaded anyway (the model lock), so a dedicated one-thread pool costs nothing and makes starving the shared pool structurally impossible.

Requests are debounced (200 ms), so arrowing through photos faster than that enqueues nothing for the ones passed through. Photos navigated past are queued behind the current photo at lower priority, to warm the cache opportunistically — their results are cached per photo, so the work stays useful if the user returns. The warm queue is bounded (32) so a long browse cannot commit the GPU to minutes of work.

4.3 The save pool — maxThreadCount=1

Also owned by FaceRecognitionController. Sidecar writes are strictly ordered by a single thread, so an older snapshot can never land after a newer one and clobber it.

Saving is split in two:

  • prepare_save() runs synchronously on the UI thread and snapshots state into a plain dict. It must stay cheap.
  • write_payload() runs on the save pool and does the serialization and disk write.

The split is what makes a save safe to run long after it was requested: the worker never touches the live catalog or gallery, only its own snapshot, so a folder switch or further labelling in the meantime cannot corrupt it.

4.4 Rules for workers

Every QRunnable in this app follows the same three rules. Breaking any of them has caused a real crash or leak:

  1. Hold a Python reference until the worker finishes. Each worker's signals object is a QObject; if the last Python reference is dropped while the worker runs, it can be collected before its queued cross-thread emit is delivered, crashing the worker thread. Hence the _pending_*_workers lists, which each callback removes itself from.
  2. Guard results with a generation counter or an identity check. Stale results — from a photo navigated away from, or a folder switched out of — must be discarded on arrival. FaceCatalog.faces_for also checks generation before caching, because the cache is keyed by filename only, so a same-named file in a different folder would otherwise get a wrong entry.
  3. Cancel, do not clear. QThreadPool.clear() drops queued runnables so they never run, never emit, and never leave the pending list — leaking the very reference keeping their signals alive. Cancellable workers instead check a threading.Event at the top of run() and exit immediately, which costs microseconds and keeps the bookkeeping honest.

4.5 Shutdown

MainWindow.closeEvent must not wait out work that could take minutes:

save library state
cancel detection work             → queued workers exit immediately
wait for detection to stop        → bounded by one in-flight photo
cancel any running folder search  → checks between photos
save face catalog
wait for pending saves            → must NOT be cancelled; a queued save must land
clear + waitForDone shared pool

Note the asymmetry: detection and search are cancelled (their results are recomputable), while saves are waited for (dropping one loses user data).

5. Persistence

Three files, all written through persistence.atomic_write_bytes, which writes to a same-directory temp file and os.replace()s it into place — atomic on POSIX and Windows alike, so a crash or full disk never leaves a truncated file.

FileScopeContents
.tamis_state.jsonper folderRatings and status per filename, plus rename bookkeeping.
.tamis_faces.jsonper folderFace boxes, confidences, embeddings, dismissals, person ids.
~/.tamis/people.json.gzglobalKnown people and their embedding samples.

Both per-folder sidecars live beside the photos, so culling state travels with the folder. Both are keyed by filename, not path — which is why a rename outside the app orphans an entry, and why faces_for must check generation before caching.

5.1 The load_error discipline

Each store distinguishes “this file does not exist yet” (normal, silent) from “this file exists but could not be read” (dangerous). Only the second sets load_error.

The distinction matters because a failed read leaves the store empty, and the next save would then overwrite a possibly-recoverable file with that empty state. Every caller must check load_error after loading and refuse any operation that would trigger a save.

It applies transitively

FaceCatalog.reconcile_people clears labels naming a person the gallery does not have — correct after Forget All Faces, catastrophic if the gallery merely failed to read, because it would clear every label in every folder opened afterwards and save the result. The caller checks PersonGallery.load_error first for exactly this reason.

5.2 Migration

Format and location changes are handled on read, never by a migration step:

  • Pre-rename sidecars (.picsel_*) are renamed in place on load.
  • ~/.picsel/people.json.gz is read as a fallback and rewritten to ~/.tamis/ on the next save.
  • Legacy embedding encodings are detected by type and converted on read.

Old files therefore keep working with no user action. The direction is one-way: once rewritten, older versions cannot read the result.

5.3 Embedding encoding

Embeddings are 512-d float32. Storing them as JSON decimal arrays cost ~12,285 characters for 2,048 bytes of real information, because json.dumps writes the full float64 repr of values that never had that precision. On a 584-photo folder this produced a 194 MB sidecar that took 3.8 s to rewrite after every labelling action.

They are now quantized to int8 with a per-vector float32 scale, base64'd into one fixed-width 688-character string:

  4 bytes   scale (float32, little-endian — pinned, since sidecars travel between machines)
512 bytes   int8 values, dequantized as  value × scale

Quantization error is at most |max|/254, which perturbs a cosine similarity by ~0.0018 — against a median gap of ~0.067 between the best and second-best candidate person, and a model whose own ambiguity is larger still. It is well below the precision the data actually carries.

Encoding is idempotent, and that is load-bearing

encode(decode(encode(v))) == encode(v), because dequantizing yields q × scale whose peak is exactly 127 × scale. That property makes codec.duplicate_key an exact match test between a freshly computed embedding and the copy of itself that went through disk — which several correctness paths depend on (§6.2). An absolute float tolerance cannot do that job, since the required threshold scales with the vector's magnitude.

6. Face recognition data model

6.1 Two stores, different scopes

FaceCatalog is per folder: which faces are in which photo, and who each one is (a person id). PersonGallery is global: who exists, and their embedding samples.

The split is why the same photo reachable from two folders gets two independent records that can be labelled differently, and why a change to the gallery has to be reconciled into folders that were not open at the time.

6.2 Sample identity

An embedding sample in the gallery carries no identity of its own — nothing links it back to the face record it came from. Everything that has to find a specific sample matches it by value, via codec.duplicate_key. That is what makes the following safe:

  • add_embedding ignores a sample the person already holds, so a double-add cannot inflate the gallery.
  • remove_embedding can find and drop the sample added under a previous label when a face is relabelled.
  • Duplicate and claimed-by-two-people samples are dropped when the gallery loads.

A duplicate sample does not improve matching — similarity_to and rank_all score a person by their single closest sample — so duplicates are pure cost. A sample held by two people is worse than cost: the same face votes for both, producing an exact tie that the suggestion then breaks arbitrarily.

6.3 Merges reach every folder

Merging two people leaves a redirect (merged_ids, persisted with the gallery) from the merged-away id to the survivor, and find_by_id resolves through it. Folders closed at merge time still name the old id; they heal on load, when FaceCatalog.reconcile_people follows redirects and clears labels naming someone who no longer exists at all.

Without the redirect, an unresolvable id read as “not labelled yet”, so re-confirming that face added a second sample instead of moving the existing one — the mechanism behind a real gallery being 34% redundant.

6.4 No confidence cutoff

There is no threshold that cleanly separates “recognized” from “not”: a genuine cross-photo match has been observed at 0.555 while unrelated siblings scored 0.61 against each other. So identify applies no similarity floor, and the UI conveys confidence continuously, by colouring a suggestion, rather than as a yes/no gate. Detector confidence is filterable, because it is cached unfiltered and the threshold slider is a free re-filter over the cached list.

7. Editing

EditSession holds the original image plus a list of operations. render() replays them from the original; undo pops the stack, so no intermediate images are retained. Adjustments (brightness/contrast/saturation) are held separately as live preview values until committed, so dragging a slider does not fill the undo stack.

Two debounces, and one that is easy to misread

EditController._adjustment_timer (30 ms) coalesces slider ticks. Because QTimer.start() restarts a running single-shot timer, a continuous drag never reaches the timeout — so no render happens while dragging, and the full-resolution render is paid once, when the drag pauses. The slider stays responsive throughout.

EditPanel._commit_timer (500 ms) commits an adjustment to undo history after a pause, so keyboard-driven slider changes (arrow keys, Page Up/Down) land in history too — sliderReleased only fires for a mouse drag.

Saving always writes through a temp file and os.replace(), so overwriting an original can never truncate it. EXIF is re-serialized from the original via getexif().tobytes() rather than passed through as a raw blob, specifically so a crop cannot leave the pre-crop framing visible in an embedded IFD1 thumbnail.

8. Testing

pytest, 218 tests, no display required — conftest.py sets QT_QPA_PLATFORM=offscreen before any PySide6 import, and provides a session-scoped QApplication plus a main_window fixture that redirects PersonGallery's default path into tmp_path so no test can touch the real ~/.tamis/people.json.gz.

Recognition tests are skipped when torch is absent (pytest.importorskip("torch")), so the suite runs in either install.

Two conventions worth keeping

Tests state the failure they prevent, not just the behaviour they assert. Most non-obvious code in this app exists because something broke; the test comment is where that is recorded.

Verify the verification. When adding a regression test, disable the fix and confirm the test actually fails. More than one test in this suite passed against the bug it was meant to catch until that was checked.
